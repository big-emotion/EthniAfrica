# Ferry — Jira Automation Setup

This file was first generated by `ferry-init` and has been edited by hand since, to
describe the rules this repository actually runs. Follow it to create or audit the
Jira Automation rules in the Jira UI.

> **Why manual?** The JSON import feature (**Automation → ⋮ → Import rules**) is beta
> and breaks across Jira Cloud releases. Creating rules manually in the UI works on
> every Jira tier (Free, Standard, Premium) and is always up-to-date.

## How dispatch works here

One workflow, `.github/workflows/ferry-router.yml`, handles every Ferry transition.
**One Jira rule feeds it**: on a status change it sends a `repository_dispatch` of
type `ferry-transition` carrying the new status as `to_status`. The router compares
`to_status` case-insensitively against the `trigger_column` values in
`ferry.config.yaml` and runs the matching agent:

| ETNI status       | Agent     |
| ----------------- | --------- |
| Refinement        | refiner   |
| READY FOR DEV     | developer |
| In Review         | reviewer  |
| Changes Requested | iterator  |
| TO MERGE          | merger    |

A status the router does not map is a **silent** no-op: the run logs "dispatch maps
to no agent" and exits green. A misspelled status therefore breaks nothing visibly —
which is why `scripts/__tests__/ferryAutomationConsistency.test.ts` holds the statuses
named in this file to `ferry.config.yaml`.

The reviewer and merger are not limited to `ferry/*` branches. They use the
`ferry/<KEY>` branch when it exists and otherwise the most recent open PR whose branch
name or title contains the ticket key — so a PR opened by `/ethniafrica-ticket` is
reviewed and merged the same way once its ticket enters In Review or TO MERGE.

## Prerequisites

- A GitHub fine-grained Personal Access Token (PAT) with **Contents: write** permission
  on `big-emotion/ethniafrica`, OR a GitHub App installation token. Replace
  `YOUR_GITHUB_PAT_WITH_REPO_SCOPE` in the rule below with that token.
- Jira Automation enabled on your project (included in all Jira Cloud tiers).

## Steps for the rule

1. Go to your Jira project → **Project settings** → **Automation**
2. Click **Create rule** (top-right)
3. Add the trigger and action as described below
4. Click **Save** — leave the rule **Disabled** until the status names match exactly
5. Enable the rule once you have verified the status names on the board

### Rule in use: Ferry — Transition (`ferry-transition`)

**Trigger:** When: Issue → Status changed → To status: `Refinement`, `READY FOR DEV`, `In Review`, `Changes Requested`, `TO MERGE`

**Action:** Send web request

- URL: `https://api.github.com/repos/big-emotion/ethniafrica/dispatches`
- Method: `POST`
- Web request body: Custom data

Headers:

| Name                   | Value                                    | Secret? |
| ---------------------- | ---------------------------------------- | ------- |
| `Accept`               | `application/vnd.github+json`            | No      |
| `Authorization`        | `Bearer YOUR_GITHUB_PAT_WITH_REPO_SCOPE` | **Yes** |
| `X-GitHub-Api-Version` | `2022-11-28`                             | No      |
| `Content-Type`         | `application/json`                       | No      |

Custom body — the fields the Ferry v1 event envelope accepts (`version`, `event_id`,
`ticket_key`, `phase`, `source` and `ts` are required; any other field is rejected):

```json
{
  "event_type": "ferry-transition",
  "client_payload": {
    "version": "v1",
    "event_id": "{{issue.key}}-{{issue.id}}",
    "ticket_key": "{{issue.key}}",
    "phase": "transition",
    "source": "jira-column",
    "ts": "{{now.jiraDate}}",
    "issue_type": "{{issue.issuetype.name}}",
    "to_status": "{{issue.status.name}}"
  }
}
```

This page was reconstructed from the router's contract, not exported from Jira. When
auditing, compare the live rule with it; the router only needs `event_type` and
`to_status` to be right, and a broader trigger is harmless because unmapped statuses
are no-ops.

## Legacy per-status rules — do not enable

Before the router, Ferry used one Jira rule and one workflow per status. The five
per-agent workflows were removed from this repository, but **the router still accepts
their event types** (`ferry-refine`, `ferry-dev`, `ferry-review`, `ferry-iterate`,
`ferry-merge`) and maps each straight to its agent. A legacy rule left enabled next to
the `ferry-transition` rule therefore runs the same agent **twice** for one transition.

> **Operator action:** the legacy **Ferry — Merge** rule (`event_type: ferry-merge`)
> still appears to be enabled in Jira and causes duplicate merger runs. Disable it in
> **Project settings → Automation**, and check that the other four legacy rules below
> are disabled too. Once all five are off, the legacy event types can be dropped from
> `ferry-router.yml`.

The sections below are kept only so an existing legacy rule can be recognised. Their
status names are corrected to the ETNI board.

### Rule: Ferry — Refine (column trigger)

**Trigger:** When: Issue → Status changed → To status: `Refinement`

Dispatches `event_type: ferry-refine` with `"phase": "refine"`.

### Rule: Ferry — Dev (column trigger)

**Trigger:** When: Issue → Status changed → To status: `READY FOR DEV`

Dispatches `event_type: ferry-dev` with `"phase": "dev"`.

### Rule: Ferry — Review (column trigger)

**Trigger:** When: Issue → Status changed → To status: `In Review`

Dispatches `event_type: ferry-review` with `"phase": "review"`.

### Rule: Ferry — Iterate (column trigger)

**Trigger:** When: Issue → Status changed → To status: `Changes Requested`

Dispatches `event_type: ferry-iterate` with `"phase": "iterate"`.

### Rule: Ferry — Merge (column trigger)

**Trigger:** When: Issue → Status changed → To status: `TO MERGE`

Dispatches `event_type: ferry-merge` with `"phase": "merge"`. **Disable it** — see the
operator action above.

## Security notes

- Mark the `Authorization` header as **secret** in the Jira UI (toggle the lock icon).
  This prevents the token from appearing in Jira audit logs.
- Rotate your PAT if it is ever exposed.
- Never commit a real token to this file — this file is safe to commit as-is since
  it only contains the placeholder `YOUR_GITHUB_PAT_WITH_REPO_SCOPE`.

## Verifying the rule works

After enabling the rule, move a Jira issue to one of the statuses above and check:

1. The Jira Automation audit log (Project settings → Automation → rule → Audit log)
2. The GitHub Actions tab on `big-emotion/ethniafrica` — exactly **one** "Ferry — Router"
   run titled `ferry-transition · ETNI-… → <status>` should appear within seconds. A
   second run titled with a legacy event type means a legacy rule is still enabled.
